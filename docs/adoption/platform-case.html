Test execution is excluded from every figure, on both sides

The suites live outside the main solution, so they are not part of the build being measured — and not part of today's numbers either. The ratio stays fair; the absolute figures are build-and-deploy only.

When test time is known, add it to both columns. It lands on the build row and leaves the promotion rows untouched — which is where most of the four-environment gain comes from. Wiring the existing suites in as a build gate is a follow-on opportunity, not a prerequisite.

What agility actually looks like

  • Containers replace machine images. An artifact is built once, pinned to a digest, and the same bytes move through dev/test → qa → cert → prod. No re-baking, no "works in qa" — there is nothing left to drift.
  • Environments stop being scarce. A VM environment is a standing cost, so we ration them. Containers make one cheap enough to create per pull request and delete when it closes — stakeholders review working software instead of a description of it.
  • Capacity follows demand. Kubernetes and Cloud Run schedule onto shared nodes and scale to zero. We stop paying 24×7 for peak capacity used at 10am.
  • Recovery is a decision, not a project. Rolling back redeploys the previous digest — one click, seconds — instead of rebuilding an image and re-running an apply.
  • Evidence is a by-product. A CycloneDX bill of materials and a CVE scan on every build, tied to the exact commit — useful when cert means what it usually means.
  • DORA measured, not estimated — lead time, deploy frequency, change failure rate, time to restore, computed from real runs.

AI is built into the pipeline, not bolted beside it

Speed only converts into agility if people don't stall. Most of the delay after a fast build isn't the machine — it's someone reading logs to work out what happened. That is where AI sits here: at every point where a person would otherwise go and find out.

The governance answers, before they're asked

  • It cannot act. The assistant has no write tools — fifteen read-only ones. A suggested action is a link to the real button, validated against the same guard that renders it. Never a shortcut around it.
  • Every call is metered and costed per feature and per model, with an advisory month-to-date budget bar. The budget warns; it never blocks.
  • It degrades to nothing. No API key and the AI actions don't appear — the platform runs exactly as it would without them.
  • It refuses rather than invents. Release notes decline to summarise a range with no recorded commit messages instead of producing confident fiction.

What it asks of us

  • A skills gap, not a technology gap. The team has not yet built or operated a modernised .NET application, nor used a pipeline like this. The adoption plan is built around closing that rather than assuming it away.
  • A period of running both pipelines, until the last component leaves the old one.
  • The modularity work itself — that's Step 2's 3×, not Step 1's 15–20×.

The parts that matter when this is all new

The platform is built so that not knowing yet is survivable:

  • A bad build can't reach users. New versions go to a parallel environment and must prove healthy before taking traffic. If they don't, they're deleted automatically — and the old version never stopped serving.
  • Rollback is one click, to the exact image that was running. Not a rebuild, not a guess.
  • Your PR gets a real environment, isolated, deleted automatically. Break it freely.
  • Production still needs a human. Protected environments hold the deploy until someone approves; rejecting applies nothing.
What you'll actually need to learn

We're not pretending there's nothing. Three things: containers (what an image is, why we pin by digest, why the app can't write to local disk); reading a deployment instead of a server (pods, restarts, health, logs); and that configuration and secrets come from the environment, not a web.config on a box.

You won't be asked to learn these alone, or in production first.

What Terraform Enterprise keeps

This does not replace infrastructure-as-code. TFE still owns clusters, networks, databases and IAM — the things that change monthly. What moves off it is application rollout, which changes hourly. Those two cadences should never have shared a tool.

Operational properties worth knowing

  • Digest-pinned and immutable. Deploys reference @sha256:…, so what was tested is bit-identical to what ships. No "the tag moved".
  • Blue-green with a health gate. The new version lands in a parallel namespace and must pass health before cutover; if it fails, that namespace is deleted and the old one never stopped serving. It's a namespace flip, not weighted traffic splitting — the honest trade for running on vanilla Kubernetes with no service mesh.
  • Event-driven handoff. CI publishes facts to RabbitMQ; the deployment service reacts. Neither calls the other. A SQL outbox/inbox makes it idempotent across retries.
  • Drift detection compares what's running against what we deployed.
  • Preview environments per PR, torn down on close, TTL-swept if the webhook is missed.

Honest caveats

Windows/.NET Framework components can't use the Linux container path until they're ported — they stay on Packer/TFE, so we run both pipelines for a period.

The platform repo has no automated test suite. Verification to date has been manual against a running system. If we depend on this in production, that gap needs closing.

Two known issues are documented and unfixed: deleted Aspire apps orphan their run history, and build attribution doesn't check the Git URL — so two repos sharing a CI job name would each claim every run.

The technology is not the risk. The risk is asking people to operate an unfamiliar runtime, on an unfamiliar pipeline, on a codebase mid-port — in production. So this plan sequences by how much new skill each step demands, not by technical convenience.

Two rules every phase obeys

  • Value before skill. Each phase pays for itself using skills the team already has.
  • Guardrails before autonomy. The safety net is switched on before the step that needs it — never after an incident proves it was needed.

1

CI only, on the repo we already have

Weeks 1–4 · new skills required: none

Point CI at the existing monolith. Change nothing about how it deploys — it keeps going out via Packer and TFE exactly as today. The team gains faster compile feedback, an SBOM and CVE scan on every build, and build history tied to commit and author.

This is the highest-value, lowest-risk step available — and the one most teams skip.

ExitEvery merge produces a build, an SBOM and a scan, and the team trusts the results enough to act on them.

2

Containerise the monolith, deploy to dev/test only

Weeks 4–12 · introduces exactly three new skills

There is no modular service to pilot with — 400 projects produce one artifact. So the pilot is the monolith itself, containerised and deployed to dev/test, while qa/cert/prod stay on Packer and TFE. This is where the 15–20× lands, and it needs no decomposition. One platform-literate engineer is paired with the team throughout — not a hand-off.

Expect this phase to be dominated by .NET Framework containerisation questions — IIS assumptions, local disk writes, session state — not by the platform.

ExitThe team deploys the monolith to dev/test unaided and can diagnose a failed deploy without escalating. If they can't, stay in this phase — don't advance on a date.

3

Promote through qa and cert

Weeks 10–18 · overlaps Phase 2

Extend up the chain — dev/test → qa → cert — leaving production on the old path. This is the phase that proves the central claim: promotion rebuilds nothing. The artifact tested in dev/test is the one that reaches cert, in about two minutes per environment instead of a fresh 2–3 hour package-and-deploy. Measure it here and put the real number in the deck.

Per-PR previews come on here too, if the monolith can stand up in one — a single large artifact may make them expensive. Defer to Phase 5 rather than forcing it.

Exitqa and cert are fed by promotion, and nobody re-packages to move between environments.

4

Production, behind an approval gate

Weeks 16–24

Business hours, pairing engineer present, rollback rehearsed before it's needed. Run it a full month before starting Phase 5 — the point is to meet a real production surprise while the support structure still exists.

Raise release cadence deliberately, not automatically. The platform makes deploy-on-every-merge possible; whether to enable it is a separate decision.

ExitOne month in production, including at least one rollback or incident handled by the team.

5

Modularity — the second increment

Month 6 onward · a further ~3×

Phases 1–4 deliver 15–20× with no code restructuring. Phase 5 attacks the only large term left — the build — by turning one artifact into ~10–20 independently buildable and deployable ones. A typical change then rebuilds one component instead of 400 projects: 30–45 min → 12–16 min.

Target the depth of the dependency graph, not the project count: if everything references one shared library, a change to it rebuilds all 400 however the pipeline is configured. Extract one component at a time, each running Phases 2–4 in miniature.

Only retire Packer/TFE for a component once it is fully across — running both pipelines is a real ongoing cost. Terraform Enterprise keeps the infrastructure.

Two honest notes on enablement

  • The AI features genuinely lower the floor. "Explain this failure", "explain this CVE", and asking the platform questions in plain English shorten the distance between an unfamiliar symptom and a plausible cause. They do not substitute for understanding — a team that leans on them exclusively will be unable to handle the case the model gets wrong.
  • Buy some expertise for the first six months. A team learning modern .NET, containers, Kubernetes and a new pipeline simultaneously, with no experienced practitioner alongside, is the single most likely way this fails. One embedded hire or contractor is cheaper than the incident that otherwise teaches the lesson.

What this plan deliberately does not do

  • No big-bang cutover. The old pipeline runs until the last component leaves it.
  • No production deploy before Phase 4. Skill is built where mistakes are cheap.
  • No date-driven advancement. Every exit is a demonstrated capability. If a team can't deploy unaided, the answer is another week of pairing — not a green tick.

What to decide now

  • Which repository gets Phase 1 — recommendation: the monolith, because it needs no porting and proves value immediately.
  • Which team owns the Phase 2 containerisation, and who pairs with them.
  • Who is the embedded expert for the first six months — hire, contract, or develop internally.
  • Whether we fund the platform's own test suite before it carries production traffic.

The first two can be decided this week. The platform is ready for Phase 1 today.
